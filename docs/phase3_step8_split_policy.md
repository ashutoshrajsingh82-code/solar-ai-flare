# Phase 3 Step 8: chronological split and rare-event audit

## Split policy

The pipeline parses observation timestamps as UTC, rejects missing, invalid, or duplicate timestamps, sorts observations stably, and creates earliest-train, middle-validation, latest-test partitions. `chronological_split` accepts either positive chronological proportions (the default 70/15/15) or both explicit UTC boundaries (`train_end`, `val_end`), interpreted as half-open intervals: `[start, train_end)`, `[train_end, val_end)`, and `[val_end, end]`. Empty partitions and invalid or unordered boundaries fail clearly.

Forecast origins belong to exactly one partition. Demo/event-derived forecast labels are generated within that partition, and the final horizon-length tail is unknown/purged because its full future interval is not available there. Independent reference labels remain untouched apart from validation and the same split-tail purge. Train-only fitted scaling remains unchanged. Causal rolling features can use earlier observations, and deep-model windows now accept prior-partition history as input context; context rows never become forecast origins or supply labels.

The classical baseline benchmark follows the same split-scoped label policy. Validation thresholds use only known validation targets; test metrics use only known test targets. Single-class or empty test horizons are reported as unavailable rather than interpreted as meaningful skill.

## Audit and scientific limits

Preprocessing writes `split_audit.json` and `split_audit.csv` under the configured pipeline artifact directory. The report records UTC bounds, partition sizes, known positive/negative forecast origins, unknown targets, observed class/event counts, synthetic/unverified/verified source status, and horizon-tail purges. Positive forecast windows and physical flare events are counted separately. The default minimum for an informative rare-event assessment is five distinct observed M/X events per partition; below that, status is explicitly inconclusive.

The repository's checked-in `backend/sample_data/demo_aditya_l1_solexs_helios.csv` and `demo_flare_events.csv` are generated by `ml/data/synthetic_generator.py`. Their classes and event counts are synthetic test/demo fixtures, not observed solar events. No genuine SoLEXS/HEL1OS observation dataset is present, so this checkout cannot provide real train/validation/test M/X counts or a scientific performance claim. A real audit requires verified observations, event reference data and provenance, and confirmed time/quality conventions. Explicit boundary dates should only be configured after inspecting that dataset; no calendar boundaries are hardcoded here.

## Verification scope

Synthetic tests exercise UTC ordering, explicit boundaries, context-only history, split-scoped target tails, distinct-event accounting and synthetic provenance. They verify implementation behavior only and do not establish real-world flare forecast skill.
