# Phase 3 Step 12: Inference and release validation

## Current scope and readiness

The backend now uses one inference path for trained classical and deep models. It loads a registry-selected model identifier, verifies the catalogued artifacts and compatibility metadata, loads the train-fitted transformer, recreates causal features from the saved manifest, checks feature order and finite model inputs, and applies the thresholds selected on validation data. An API caller can select a registered `model_id`; arbitrary paths are never accepted.

Model scores are uncalibrated classification scores. The displayed risk category is a score bucket, not a calibrated event probability. Forecast labels mean that an M/X-class flare onset was labeled within `(origin, origin + horizon]`; horizons are 1, 3, 6, 12, and 24 hours. The output does not predict an exact event time. Coverage-aware unknown labels remain unknown during training and evaluation.

The current checkout does not contain a verified operational solar model artifact or observational test dataset. The bundled data and the deterministic inference fixture are synthetic. The inference path and locally trained CPU baseline are integration-tested, but this repository is an **integration-tested prototype**, not a deployment candidate or production-ready service. Authentication/tenant isolation, deployment orchestration, external data freshness, production database operations, and observational skill validation remain deployment requirements.

## Configure and start locally

The backend reads `DATA_MODE` (`demo` by default), `DATABASE_URL` (SQLite by default), `MODEL_DIR` (`./ml/saved_models`), `SAMPLE_DATA_DIR` (`./sample_data`), `PIPELINE_ARTIFACT_DIR`, and `CORS_ORIGINS`. Relative SQLite paths resolve against `backend/`. `CORS_ORIGINS` must be an explicit comma-separated origin list; wildcard origins are rejected. No credentials are required for the local demo configuration.

From the repository root:

```powershell
cd backend
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

The app initializes its database at startup and, in `DATA_MODE=demo`, loads the bundled demonstration data. For the frontend, in another terminal:

```powershell
cd frontend
npm ci
npm run dev
```

The frontend uses same-origin `/api` requests through the Vite proxy. `docker-compose.yml` is available for local container startup; its production suitability has not been validated.

## Train and version artifacts

Run the data pipeline through the existing UI/API, then submit a supported `TrainRequest` to `POST /api/models/train`. The worker trains on the train partition, selects per-horizon thresholds from validation only, evaluates the frozen model/thresholds on the chronological test partition, and registers the version. Supported families are the baseline/rule estimators in `ml.models.baseline` and `cnn_1d`, `lstm`, `cnn_lstm_fusion`, `cnn_transformer`, and `dlstm`. A family is available only after a model has actually trained and its model, preprocessor, evaluation report, and feature manifest artifacts pass integrity and compatibility checks.

Each model registry entry has a model ID and version. The catalog stores SHA-256, byte size, storage key, and compatibility fields for every artifact. The feature manifest records ordered feature definitions, feature schema, training/validation/test periods, source fingerprint, train-only preprocessing configuration and fitted parameters, label contract, random seed, dependency versions, model architecture, and training configuration. Historical manifest schema v1 remains loadable; newly created manifests use v2. Serialized joblib artifacts are trusted local outputs only: do not put user-supplied or third-party joblib files in the configured model directory.

Inspect `GET /api/models` for public metadata/readiness, `GET /api/models/{model_id}/readiness` for a single version, and `GET /api/models/{model_id}/metrics` for evaluation metadata. `POST /api/models/select` sets the default version. `POST /api/predict` may instead select a particular registered `model_id` per request.

## Prediction request and response

The request accepts 1–10,000 timestamped raw rows. Timestamps must be valid, strictly increasing, and unique. Flux values must be numeric, finite when present, and nonnegative; missing values are never imputed. Cadence deviations are returned as warnings, and a model requiring unavailable feature history returns HTTP 422. Invalid artifacts or no active model return HTTP 503; unknown model IDs return HTTP 404. Each model manifest determines how much history its features require; there is no universal minimum window.

A complete **request and response generated by executing the CPU inference path** is saved in [`phase3_step12_inference_example.json`](../backend/reports/phase3_step12_inference_example.json). It uses a fitted logistic-regression artifact and 150 one-minute rows from the deterministic test fixture. Those values are synthetic, and the scores are not evidence of forecast skill. The generated response marks scores uncalibrated, includes model version and validation-selected thresholds, and states the forecast periods as `(forecast_origin, forecast_origin + horizon]`. Historical labels and future outcomes are not returned as if known at prediction time.

Successful synchronous predictions are persisted in the existing `inference_history` table. `input_snapshot` contains output metadata, quality summaries, and time ranges, not the raw observation payload. Retrieve one with `GET /api/predict/{prediction_id}`. The response includes a prediction identifier and measured inference latency; structured logs include request/model IDs and outcome categories without logging raw input rows. The lightweight `/api/health` and `/api/health/ready` endpoints do not deserialize models; `/api/health/ml` reports model readiness after validating the active artifacts and caches the result for 30 seconds.

## Checks and local evidence

Run tests from `backend/`:

```powershell
python -m pytest tests/test_production_inference.py -q
python -m pytest -q
```

The focused suite exercises an actually fitted CPU logistic-regression artifact through the saved transformer, causal feature function, manifest validator, thresholds, database persistence, and retrieval route. It also covers corrupted artifacts, insufficient rolling history, invalid/unsorted/duplicate timestamps, cadence warnings, and a future-value leakage check. API functions and schemas are checked directly; the Windows `TestClient` HTTP boundary currently stalls, so network-level API behavior is not claimed as verified.

Lint, formatting, and type-check commands are not configured in this repository. `python -m compileall -q app ml tests` is the available syntax check. The full pytest suite includes `tests/test_api.py`; the health handler now avoids loading model artifacts, while the API suite should be rerun on the deployment host.

## Operational limits

- No score calibration has been implemented and validated.
- The demo dataset is synthetic; source metadata and generated labels cannot establish observational forecast performance.
- No validated operational GOES/SoLEXS/HEL1OS feed or ground-truth evaluation is included here.
- Cadence deviations and missingness are reported, but population-level drift or forecast-performance monitoring is not established.
- SQLite and the JSON registry are suitable for local single-instance development. Multi-worker consistency, backup/restore, authorization, load tests, deployment hardening, and production incident monitoring have not been verified.
- Readiness validates catalog hashes and model compatibility; it does not establish scientific validity or deployment security.
